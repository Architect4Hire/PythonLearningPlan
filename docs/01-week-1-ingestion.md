#### 3. The `SourceFile` model and repo walker

`coderag/models.py`:

```python
from pathlib import Path
from pydantic import BaseModel, Field

class SourceFile(BaseModel):
    id: str                      # stable hash of repo-relative path
    path: str                    # repo-relative, forward slashes
    language: str                # "csharp" | "markdown" | "xml" | ...
    text: str
    line_count: int
    byte_size: int
    project: str | None = None   # nearest enclosing .csproj
    is_test: bool = False

```

Repo-relative paths with forward slashes, always. Absolute paths leak your home directory into every citation and break the moment you containerise on Day 23.

#### 4. Exclusions — the part that matters

`coderag/ingest.py`:

```python
import hashlib, re
from pathlib import Path
import pathspec

EXCLUDED_DIRS = {
    "bin", "obj", ".vs", ".git", ".idea", "packages",
    "node_modules", "TestResults", "artifacts", "_ReSharper.Caches",
}

EXCLUDED_GLOBS = [
    "*.Designer.cs", "*.g.cs", "*.g.i.cs", "*.generated.cs",
    "*AssemblyInfo.cs", "*.feature.cs", "*.razor.g.cs",
]

INCLUDED_SUFFIXES = {
    ".cs": "csharp",
    ".csproj": "xml", ".props": "xml", ".targets": "xml",
    ".md": "markdown",
    ".json": "json",       # appsettings, but see below
    ".sql": "sql",
}

AUTOGEN_MARKER = re.compile(r"<auto-?generated", re.IGNORECASE)

def is_generated(text: str) -> bool:
    """Roslyn and most scaffolders emit this in the first few lines."""
    return bool(AUTOGEN_MARKER.search(text[:2000]))
```

Four layers of filtering, and you need all four:

| Layer | Catches |
|---|---|
| Directory names | Build output, package caches — the bulk by volume |
| Filename globs | Designer files, T4 output, scaffolded partials |
| `.gitignore` via `pathspec` | Whatever else this specific repo excludes |
| `<auto-generated>` header scan | Everything the first three miss |

**Why this matters more than it sounds.** A mid-size solution can be 60% machine-generated by line count. Generated code is highly repetitive, so it embeds into a dense cluster that sits near everything and is relevant to nothing. Index it and your top-10 results fill with `InitializeComponent` variants. Every hour you spend on retrieval quality in Week 3 is wasted if you skipped this.

A judgement call to make now: **`Migrations/`**. EF migrations are technically hand-triggered but machine-written, enormous, and almost never what anyone is looking for. I'd exclude them and note the decision. If someone asks "when did we add the `Orders.DiscountCode` column" you'll want them back — but that's a different retrieval problem.

Second judgement call: **test files**. Keep them, but tag `is_test=True` so you can filter either way later. Tests are frequently the best documentation of intended behaviour in a codebase, and "show me how this is used" is a common query that tests answer well.

#### 5. Walk and report

```python
def walk_repo(root: Path) -> list[SourceFile]:
    spec = _load_gitignore(root)
    files: list[SourceFile] = []
    for p in root.rglob("*"):
        if not p.is_file():
            continue
        if any(part in EXCLUDED_DIRS for part in p.parts):
            continue
        rel = p.relative_to(root).as_posix()
        if spec and spec.match_file(rel):
            continue
        if any(p.match(g) for g in EXCLUDED_GLOBS):
            continue
        lang = INCLUDED_SUFFIXES.get(p.suffix.lower())
        if lang is None:
            continue
        try:
            text = p.read_text(encoding="utf-8-sig")
        except (UnicodeDecodeError, OSError):
            continue
        if lang == "csharp" and is_generated(text):
            continue
        files.append(SourceFile(
            id=hashlib.sha256(rel.encode()).hexdigest()[:16],
            path=rel,
            language=lang,
            text=text,
            line_count=text.count("\n") + 1,
            byte_size=len(text.encode()),
            is_test=_looks_like_test(rel),
            project=_nearest_csproj(p, root),
        ))
    return files
```

Note `encoding="utf-8-sig"`. Visual Studio writes UTF-8 BOMs into `.cs` files constantly, and a stray `\ufeff` at the start of a file will confuse your parser on Day 2 in a way that takes a while to spot.

`scripts/stats.py` should print: total files, total lines, breakdown by extension, breakdown by project, count of files excluded and why.

## Day 2 — Tue 28 Jul · Parsing C# with tree-sitter

**What you're learning today:** how to get structure out of source code. This is the day that separates a code RAG system from a text search system.

### Hard block (2 hrs)

#### 1. Why tree-sitter and not Roslyn

You're a C# engineer, so the obvious question is why not use Roslyn, which understands C# properly. Three reasons:

- **It doesn't need to compile.** Tree-sitter is error-tolerant — it parses a file with syntax errors, half-finished code, or missing references, and gives you a tree with error nodes in the broken parts. Roslyn's semantic model wants a working build.
- **It's the same interface for every language.** When you add TypeScript or SQL to this index in month two, it's a different grammar and identical code.
- **It's fast.** Milliseconds per file, and incremental.

The tradeoff is real and you should know it: tree-sitter is **syntactic, not semantic**. It can tell you a method is called `Handle` and that it's inside `CreateOrderCommandHandler`. It cannot tell you that `_repository` is an `IOrderRepository` unless the declaration is in the same file. For Week 4's symbol graph this limitation will bite, and you'll work around it with heuristics.

```bash
uv add tree-sitter tree-sitter-c-sharp
```

#### 2. First parse

```python
import tree_sitter_c_sharp as tscs
from tree_sitter import Language, Parser

CSHARP = Language(tscs.language())
parser = Parser(CSHARP)

source = path.read_bytes()          # BYTES, not str
tree = parser.parse(source)
root = tree.root_node
```

**Two gotchas, both of which will cost you an hour if you hit them cold:**

*Bytes, not characters.* Tree-sitter works entirely in byte offsets. `node.start_byte` and `node.end_byte` index into the raw bytes. If you parse a decoded string, or slice the decoded string with byte offsets, everything is subtly wrong the moment a non-ASCII character appears — a `£` in a comment, a smart quote in a string literal. **Always slice bytes, then decode:**

```python
text = source[node.start_byte:node.end_byte].decode("utf-8")
```

*API churn.* The Python bindings changed shape across versions. In current versions `Parser(LANGUAGE)` works; older ones need `p = Parser(); p.set_language(LANGUAGE)`. Similarly `query.captures()` returns a dict of `{capture_name: [nodes]}` in recent versions and a list of `(node, name)` tuples in older ones. Check what yours does in the REPL before writing against it — five minutes now, versus debugging an empty result set later.

#### 3. Walk the tree and see what's there

```python
def dump(node, source: bytes, depth: int = 0, max_depth: int = 4) -> None:
    if depth > max_depth:
        return
    snippet = source[node.start_byte:node.end_byte].decode("utf-8", "replace")
    snippet = snippet.split("\n")[0][:60]
    print(f"{'  ' * depth}{node.type:35} {snippet}")
    for child in node.named_children:
        dump(child, source, depth + 1, max_depth)
```

Run this on a handler class from your own repo. Spend real time here — ten minutes reading actual tree output teaches you more than any documentation.

`named_children` skips anonymous nodes (braces, semicolons, keywords). You almost always want it.

#### 4. The node types that matter for C#

```python
TYPE_DECLARATIONS = {
    "class_declaration", "interface_declaration", "struct_declaration",
    "record_declaration", "record_struct_declaration", "enum_declaration",
}

MEMBER_DECLARATIONS = {
    "method_declaration", "constructor_declaration", "destructor_declaration",
    "property_declaration", "indexer_declaration", "operator_declaration",
    "conversion_operator_declaration", "event_declaration",
    "field_declaration", "delegate_declaration",
}

NAMESPACE_DECLARATIONS = {
    "namespace_declaration",              # classic braced
    "file_scoped_namespace_declaration",  # C# 10+  namespace Foo;
}
```

**Do not miss `file_scoped_namespace_declaration`.** Modern C# uses file-scoped namespaces almost universally, and it's a structurally different node from the braced form. Handle only the braced one and every chunk from a modern codebase loses its namespace — which is exactly the metadata you most need for the context header on Day 3.

#### 5. Extract symbols

```python
class Symbol(BaseModel):
    kind: str                  # "class" | "method" | "property" | ...
    name: str
    signature: str             # declaration line(s), no body
    namespace: str | None
    parent_type: str | None    # enclosing type name
    modifiers: list[str]       # public, static, async, override...
    start_line: int            # 1-based
    end_line: int
    start_byte: int
    end_byte: int
    doc_comment: str | None    # /// <summary> above the declaration
    file_path: str
```

Getting the name uses field accessors rather than positional children:

```python
name_node = node.child_by_field_name("name")
name = source[name_node.start_byte:name_node.end_byte].decode() if name_node else "<anon>"
```

Field names are grammar-defined and stable. Positional indexing into `children` is not — it breaks the moment someone adds an attribute or an access modifier.

**XML doc comments are a separate problem.** `/// <summary>` blocks are not children of the declaration node; they're `comment` siblings immediately preceding it. You must walk backwards from the declaration, collecting contiguous `comment` siblings, and stop at the first blank line or non-comment node:

```python
def preceding_doc(node, source: bytes) -> str | None:
    parts: list[str] = []
    sib = node.prev_named_sibling
    while sib is not None and sib.type == "comment":
        text = source[sib.start_byte:sib.end_byte].decode("utf-8", "replace")
        if not text.lstrip().startswith("///"):
            break
        parts.append(text)
        sib = sib.prev_named_sibling
    return "\n".join(reversed(parts)) if parts else None
```

This matters a lot. A doc comment is a human-written natural-language description of a method — it's by far the most retrievable text attached to that symbol, and dropping it is a significant unforced recall loss.

Also capture attributes (`[HttpGet("/orders/{id}")]`) the same way — they're siblings too, and routing attributes make endpoints findable by URL, which people absolutely will search for.

### Consolidation (1–1.5 hrs)

1. **Token density measurement.** Take five files — a controller, a domain entity, a `.csproj`, a README, an `appsettings.json` — and compute characters per token with `tiktoken` for each. Write the ratios into `NOTES.md`. You'll use them on Day 3 to set chunk budgets, and the spread between prose and C# will be larger than you expect.
2. **Parse the whole repo, count error nodes.** Walk every file, count nodes of type `ERROR`. A healthy parse rate is >99% of files clean. If it's lower, look at the failures — usually one preprocessor-heavy file or an encoding issue.
3. **Symbol census.** Total symbols by kind. A 100k-line C# solution typically yields 4,000–10,000 members. That number is your chunk count ballpark, and it's your first real sense of index scale.

## Day 3 — Wed 29 Jul · Chunking with context headers

**What you're learning today:** that the unit you embed is a design decision, not a mechanical split — and that a chunk needs to carry its own context.

### Hard block (2 hrs)

#### 1. The chunk model

```python
class Chunk(BaseModel):
    id: str
    file_id: str
    file_path: str
    language: str
    kind: str                  # "method" | "type" | "members" | "prose"
    symbol_name: str | None
    namespace: str | None
    parent_type: str | None
    project: str | None
    is_test: bool
    start_line: int
    end_line: int
    header: str                # context header, prepended at embed time
    body: str                  # the actual source
    token_count: int

    @property
    def embed_text(self) -> str:
        return f"{self.header}\n{self.body}"
```

Keeping `header` and `body` separate matters. You embed `header + body`, but you show the model `body` with the header rendered differently — and when you display a citation to a user, you show neither, you show the file path and line range.

#### 2. The context header

This is the highest-leverage twenty lines you'll write this week.

```python
def build_header(sym: Symbol, file: SourceFile) -> str:
    lines = [f"// File: {file.path}"]
    if file.project:
        lines.append(f"// Project: {file.project}")
    if sym.namespace:
        lines.append(f"// Namespace: {sym.namespace}")
    if sym.parent_type:
        lines.append(f"// Type: {sym.parent_type}")
    lines.append(f"// {sym.kind.title()}: {sym.signature}")
    if file.is_test:
        lines.append("// Context: test code")
    if sym.doc_comment:
        lines.append(f"// Doc: {_flatten_xml_doc(sym.doc_comment)}")
    return "\n".join(lines)
```

Recall the example from the primer. Without a header, this chunk is invisible to the question "how are orders created in the ordering service":

```csharp
public async Task<Guid> Handle(CreateOrderCommand request, CancellationToken ct)
{
    var order = Order.Create(request.CustomerId, request.Items);
    await _repository.AddAsync(order, ct);
    return order.Id;
}
```

With the header, the words *Ordering*, *Application*, *Orders*, *CreateOrderCommandHandler*, *Handle*, *CreateOrderCommand* are all in the embedded text. Costs ~40 tokens. Typically returns 10–20% recall.

`_flatten_xml_doc` should strip the `///` and the XML tags and leave the prose. `<summary>Creates a new order for the customer.</summary>` → `Creates a new order for the customer.` The tags are noise; the sentence is gold.

#### 3. Chunking strategy by size

Not every symbol becomes one chunk. Three cases:

**Normal members (20–400 tokens)** — one chunk each. The common case, and most of your index.

**Oversized members (>400 tokens)** — a 300-line method exists in every real codebase. Split it, but repeat the signature and header on every piece, and mark continuation:

```
// [continued 2/3] CreateOrderCommandHandler.Handle(...)
```

Prefer splitting at statement boundaries from the AST rather than at token counts. Blank lines within a method body are a decent cheap proxy if AST-level splitting gets fiddly.

**Tiny members (<25 tokens)** — auto-properties, one-line fields, simple constructors. Individually these are near-useless chunks: `public Guid Id { get; set; }` retrieves against everything and informs nothing. **Merge consecutive small members of the same type into one `members` chunk** under a shared header. This typically cuts your chunk count by 30–40% and improves precision, because you stop returning a dozen trivial property chunks in every result set.

**Interfaces and enums** — keep whole regardless of size. They're cohesive, usually small, and splitting an interface into individual method signatures destroys the thing that makes it meaningful.

#### 4. Type-level summary chunks

For each type, emit an additional chunk containing the class declaration, its doc comment, its field declarations, and the *signatures only* of its members:

```
// File: src/Ordering.Application/Orders/CreateOrderCommandHandler.cs
// Type: CreateOrderCommandHandler : IRequestHandler<CreateOrderCommand, Guid>
// Doc: Handles creation of new customer orders.

public class CreateOrderCommandHandler : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly IOrderRepository _repository;
    private readonly ILogger<CreateOrderCommandHandler> _logger;

    public CreateOrderCommandHandler(IOrderRepository repository, ILogger<...> logger);
    public Task<Guid> Handle(CreateOrderCommand request, CancellationToken ct);
}
```

This is the "small-to-big" pattern from the primer, applied to code. Questions split cleanly into two kinds — *"what is this class for"* and *"how does this specific thing work"* — and they want different granularities. Type summaries answer the first. Method chunks answer the second. Having both roughly doubles your index size and is worth it.

#### 5. Non-code files

Markdown gets header-based chunking: split on `#`/`##`, keep the heading path as the header, never split a fenced code block. `.csproj` and `appsettings.json` get one chunk per file (they're small and only meaningful whole).

A note on `appsettings.json`: **check for secrets before indexing.** Connection strings with passwords, API keys in a `.Development.json` someone committed years ago. Grep for them and exclude. You're about to send this content to an API.

### Consolidation (1–1.5 hrs)

1. **Read 20 random chunks in full.** Not the metadata — the actual `embed_text`. For each, ask: if this were the only thing I saw, would I know what it is? Fix the header until the answer is yes.
2. **Chunk size distribution.** Histogram the token counts. You want a hump in the 50–300 range, a small tail above, and — after merging — nothing much under 25.
3. **Chunk count sanity.** Members × ~1.3 (splits and type summaries) should land in the 5,000–15,000 range for a mid-size solution. Wildly outside that means a bug: usually a merge that isn't merging or an exclusion that isn't excluding.
4. **Test:** every byte of every non-excluded `.cs` file appears in at least one chunk, or is deliberately dropped (using directives, closing braces). Assert this. Silent content loss is the worst bug class here because nothing fails — answers just quietly aren't there.

### Reading (30 min)

Small-to-big and parent-document retrieval patterns. The core insight to internalise: **the optimal unit for matching is smaller than the optimal unit for answering.**

### ✅ Done when

- `python -m scripts.chunk_stats` prints count, distribution, and kind breakdown
- 20 hand-read chunks are all self-describing
- Coverage test green
- No secrets in the chunk set

## Day 4 — Thu 30 Jul · Embeddings and the vector index

**What you're learning today:** what an embedding actually is, by computing similarity yourself before letting a library do it.

### Hard block (2 hrs)

#### 1. A code embedding model

```bash
uv add sentence-transformers chromadb einops
```

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer(
    "jinaai/jina-embeddings-v2-base-code",
    trust_remote_code=True,
)
```

`trust_remote_code=True` is required — the model ships custom modelling code. Read what you're running if that makes you uncomfortable; it should at least make you pause.

768 dimensions, 8192 token context, ~161M parameters. On CPU expect roughly 30–80 chunks/second depending on chunk size and core count. 8,000 chunks is therefore a few minutes, not hours. Time your first full run and write it down — you'll re-index a lot in Week 3.

**Why not `bge-small-en-v1.5`?** It's trained overwhelmingly on prose. Code-specific models are trained on code and docstrings paired together, which is precisely your retrieval task: natural-language question → code. You'll benchmark this claim against your own golden set in Week 3 rather than taking it on faith — that comparison is one of the more instructive experiments in the plan.

#### 2. The `Embedder` behind a protocol

```python
from typing import Protocol, runtime_checkable
import numpy as np

@runtime_checkable
class Embedder(Protocol):
    dimension: int
    def embed_documents(self, texts: list[str]) -> np.ndarray: ...
    def embed_query(self, text: str) -> np.ndarray: ...
```

Two separate methods, not one. Some models want an instruction prefix on queries but not documents (bge does; jina-code doesn't). Encoding that asymmetry in the interface from day one means switching models in Week 3 is a config change rather than a hunt through call sites.

This is your structural-typing moment. Nothing declares `implements Embedder`. `LocalEmbedder` satisfies it by having the right methods, and mypy checks that statically. Coming from C#, the useful mental note: the interface exists at the *call site's* expectations, not the implementation's declaration.

Normalise to unit length on output. Then cosine similarity is just a dot product, and every downstream comparison gets simpler.

#### 3. Chroma behind a `VectorStore` protocol

```python
import chromadb

client = chromadb.PersistentClient(path="./chroma")
collection = client.get_or_create_collection(
    name="code_v1",
    metadata={"hnsw:space": "cosine"},
)
```

Set the distance metric explicitly. Chroma's default is L2, and with normalised vectors L2 and cosine rank identically — but the *scores* differ, and you will confuse yourself in Week 3 comparing runs if you leave it implicit.

Name the collection with a version suffix. Week 3 has you sweeping configurations, each needing its own index, and `code_v1` / `code_chunk512` / `code_bge` will keep you sane.

Metadata to store per chunk — all of it filterable later:
`file_path`, `language`, `kind`, `symbol_name`, `namespace`, `parent_type`, `project`, `is_test`, `start_line`, `end_line`.

Upsert in batches of 256. One call per chunk is dramatically slower and you'll feel it at 8,000 chunks.

#### 4. Index the repo

`scripts/index.py`: walk → parse → chunk → embed → upsert, with a `rich` progress bar. Run it. Note the wall-clock time.

### Consolidation (1–1.5 hrs)

1. **Write cosine similarity by hand.**

```python
def cosine(a: np.ndarray, b: np.ndarray) -> float:
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
```

Embed three chunks — two doing similar things in different classes, one unrelated — and check the numbers behave. Then verify your values match what Chroma returns. **Chroma gives distance, not similarity**: with cosine space, `similarity = 1 - distance`. Confirm they agree to four decimal places. If they don't, find out why before you build anything on top.

2. **The retrieval smoke test.** Embed five natural-language questions about your repo and print the top 10 chunks for each with scores. Don't build a CLI, just print. You are looking for: does the right file appear at all, and at what rank? Write the ranks down. **This is your true pre-baseline** — the number Week 3 exists to improve.

3. **Look at what surprises you.** There will be a query where something absurd ranks first. Open that chunk and work out why. Usually it's a chunk that's too short, or one whose header dominates its body.

### Reading (30 min)

The `jina-embeddings-v2-base-code` model card, then skim the MTEB leaderboard's code retrieval tasks (CodeSearchNet, CoIR). Work out what those benchmarks actually measure and why topping an average doesn't guarantee anything about your specific repo.

## Day 5 — Fri 31 Jul · Retrieval, generation, and a working system

**What you're learning today:** how retrieved context becomes an answer, and why prompt construction is engineering rather than wording.

### Hard block (2 hrs)

#### 1. Retrieval

```python
class ScoredChunk(BaseModel):
    chunk: Chunk
    score: float
    rank: int
```

`retrieve(query: str, k: int = 15) -> list[ScoredChunk]`.

**k=15, not 5.** Code chunks are small — a method is often 80 tokens. Five of them is 400 tokens of context, which is nothing. Start at 15 and tune it properly in Week 3 once you can measure.

#### 2. Prompt construction

Three parts, and the middle one is where the craft is.

**System prompt:**

```
You are a code comprehension assistant for a C# codebase.

Answer only from the provided code excerpts. Every claim must cite the
excerpt it came from using [n].

If the excerpts do not contain the answer, say exactly what is missing
rather than inferring from general C# knowledge. A confident wrong answer
about someone's codebase is worse than "the provided code doesn't show this."

When describing behaviour, reference specific types and members by name.
```

The abstention instruction is doing heavy lifting. The model knows a great deal of general C# and will happily describe how a typical `IOrderRepository` works rather than how *yours* does. That's the dominant faithfulness failure mode for code RAG, and Day 16 attacks it properly.

**Context block:**

```
[1] src/Ordering.Application/Orders/CreateOrderCommandHandler.cs:24-38
    CreateOrderCommandHandler.Handle(CreateOrderCommand, CancellationToken)

public async Task<Guid> Handle(CreateOrderCommand request, CancellationToken ct)
{
    ...
}
```

File path and line range on the citation line, so a citation maps to something a human can open. Signature line so the model knows what it's looking at without parsing.

**Ordering matters.** Because of the lost-in-the-middle effect, put the highest-scored chunks at the *edges* of the context block — best first, second-best last, weakest in the middle. It's a two-line change and it measurably helps. You'll verify it yourself in Week 3.

#### 3. Generation and the answer model

```python
class Citation(BaseModel):
    index: int
    file_path: str
    start_line: int
    end_line: int
    symbol_name: str | None

class Answer(BaseModel):
    question: str
    text: str
    citations: list[Citation]
    retrieved: list[ScoredChunk]
    latency_ms: dict[str, float]
```

Temperature 0.0. You are doing factual retrieval; there is nothing to be gained from sampling diversity, and you need reproducibility for Week 2's evals.

Keep `retrieved` on the answer even though the user never sees it. On Day 6 that becomes your trace, and every debugging session for five weeks starts by reading it.

### Consolidation (1–1.5 hrs)

Not a refactor today. Today you find out what you've built.

**Ask 20 questions you know the answers to**, deliberately spread across categories:

| Category | Count | Example |
|---|---|---|
| Symbol lookup | 5 | "Where is the retry policy configured?" |
| Behaviour | 5 | "What happens when order validation fails?" |
| Cross-cutting | 4 | "Which classes implement IOrderRepository?" |
| Trace | 3 | "What calls SendConfirmationEmail?" |
| Unanswerable | 3 | Something plausible your repo genuinely lacks |

For each, record: verdict (correct / wrong / hallucinated / correctly refused), and for failures, the **class** — recall, precision, or faithfulness. Open the retrieved chunks to tell them apart; you cannot classify from the answer alone.

Then tally by class in `NOTES.md`. **This tally is a prediction.** Mostly recall failures → hybrid retrieval (Day 14) is your big win. Mostly precision → reranking (Day 15). Mostly faithfulness → prompt work (Day 16). You'll check the prediction in three weeks.

Expect the cross-cutting and trace questions to fail badly. Pure similarity search can't answer "what calls X" — the answer isn't textually similar to the question. That gap is exactly what Week 4's symbol graph exists to close, and feeling the failure now is why it's worth building later.
